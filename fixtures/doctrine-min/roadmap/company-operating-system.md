# MSTRMND Company Operating System Roadmap

## Objective

Develop `mstrmnd.md` into the canonical, agent-readable source of truth for MSTRMND's company doctrine, platform architecture, commercial model, delivery standards, skills, connectors, brand, research, and roadmap.

## Phase 1 — Canonical Foundation

Establish the core source of truth:

- company philosophy and canon;
- positioning and terminology;
- offer and sales doctrine;
- intelligence architecture;
- agent, skill, and connector standards;
- security, evaluation, and observability;
- brand and research standards.

**Completion test:** a new human or agent can explain what MSTRMND is, how it operates, what it sells, and what rules govern its systems.

## Phase 2 — Implementation Specifications

Add technical and operational details:

- context-engine specification;
- memory model and retention rules;
- model router and provider policy;
- workflow runtime specification;
- tool and skill registries;
- tenant and identity model;
- approval architecture;
- observability schema;
- evaluation harness;
- reference deployment architecture.

**Completion test:** engineering can derive a platform backlog and interfaces directly from the documentation.

## Phase 3 — Domain Agents and Skills

Define production-ready capability packs:

- operator;
- sales and revenue operations;
- voice and customer intake;
- content and creative media;
- software engineering;
- research and intelligence;
- executive decision support;
- quality and evaluation.

Each pack should include agent specifications, skills, workflows, tools, permissions, evaluations, and example deployments.

**Completion test:** a client solution can be assembled from reusable governed components rather than designed from zero.

## Phase 4 — Connectors and Client Blueprints

Create implementation documentation for priority systems and verticals:

- communication, calendar, CRM, commerce, code, data, deployment, knowledge, and media connectors;
- professional services;
- agencies and production;
- logistics and field services;
- ecommerce;
- legal and regulated administration;
- media and entertainment;
- software companies.

**Completion test:** discovery findings map to known connector patterns, workflow templates, risks, and commercial modules.

## Phase 5 — Executable Knowledge System

Transform static documentation into machine-operable configuration:

- structured schemas for agents, skills, tools, workflows, policies, and evaluations;
- generated `AGENTS.md`, `CLAUDE.md`, and environment-specific instruction bundles;
- documentation validation and link checking;
- versioned releases;
- automated indexing and retrieval;
- provenance and change history;
- synchronization with platform registries.

**Completion test:** platform runtimes and developer agents consume the same versioned source of truth used by the human team.

## Phase 6 — MSTRMND Core Review

Review the separate `mstrmnd-core` repository to determine whether it should become:

- the executable implementation of this doctrine;
- a reusable platform starter;
- the orchestration runtime and registries;
- or an archived/merged project.

Evaluation criteria:

- architectural alignment;
- current stack and code quality;
- overlap with this repository;
- portability and model independence;
- security and tenant isolation;
- workflow durability;
- observability and evaluation readiness;
- effort to modernize versus rebuild.

## Governance

- `main` represents approved company doctrine.
- Material changes use pull requests with explicit rationale.
- Files should have clear owners and revision history.
- Conflicting instructions should be resolved at the highest relevant canonical layer.
- Documentation that no longer reflects the company should be revised or retired rather than silently ignored.
